# 位标批量路线规划 (Bookmark Route Planner)

> 规格文档 · 分支 `feature/route-planner` · 基线 `d97a6c7` · 2026-08-21
> 通过 `/interview-me` 访谈 + 红队对抗评审产出

---

## 1. 问题陈述

用户在 EVE Online 中会收到成批的**位标**（bookmark）文本，通常是别人从游戏内「位置」窗口复制粘贴到群里的。每条位标落在某个星系里。用户需要驾船依次走访这些星系。

**现状**：用户自己在脑子里排顺序 —— 「我从 XXX 开始，然后怎么怎么走，能尽可能多的把所有点都过一遍」。点数常常是几十个，手工排既慢又排不好。

**目标**：粘贴位标文本 → 程序解析出星系 → 自动算出走访顺序 → 按"线"分段展示 + 画在地图上 + 推送到游戏内航点。

---

## 2. 目标与非目标

### 目标

- 解析游戏内「位置」窗口复制出的位标文本，提取星系
- 以当前角色所在星系为起点，规划一条走访全部位标星系的路线
- 星门为主要移动方式；当星门绕远且直线距离在旗舰跳跃射程内时，改用旗舰跳
- 在旗舰跳处把路线切成若干条「线」，逐条应用到游戏内航点

### 非目标（访谈中明确排除）

| 排除项 | 原因 |
|---|---|
| 跳跃疲劳建模 | 用户明确「疲劳你不管就行」，自己心里有数 |
| 耗时 / ETA 计算 | 用户明确「耗时不要」 |
| 位标名称里的倒计时（`2d21h` / `仅18h` / `POS 中国时间22日23点结束`）参与排序 | 用户明确「不需要倒计时」。格式极不统一，解析不可靠 |
| 限时最大覆盖 / 定向问题 | 全部点都要走到，不做取舍 |
| 高安路段 | 「不会去高安，我们只会在 nullsec 做这个事」 |
| 位标本身的坐标（同星系内哪个位标先去） | 只精确到星系级 |

## 3. 输入格式与解析

### 3.1 实测样本格式

游戏内「位置」窗口复制出来的是 **Tab 分隔的 9 列**：

```
名称 ⇥ 类型 ⇥ 跳数 ⇥ 星系 ⇥ 星座 ⇥ 区域 ⇥ 创建时间 ⇥ 备注 ⇥ 创建者
```

真实行示例：

```
BKG-Q2 护盾加强母星 2天19H	坐标	3	BKG-Q2	0C-PZ4	血脉	2026.08.20 19:02	-	Baiweia
位于XW-2XP*星系2天19小时	坐标	6	XW-2XP	8-IL7S	血脉	2026.08.20 16:16	-	Nujabess
古斯塔斯旗舰集结地/2d23h	坐标	3	M-HU4V	BZ-10K	血脉	2026.08.20 11:30	-	Tak1i
```

样本统计：**68 行 → 42 个不重复星系**，分布在 11 个星座，全部位于 血脉 (Branch) 区域。

### 3.2 解析规则

1. **按行切分**，每行按 `\t` 切成字段
2. **优先取索引 3**（星系列）。若该字段能被解析为星系 → 采用
3. **回退**：列数不足 9 或索引 3 解析失败时，扫描所有字段，取第一个能解析成星系的 —— 但**跳过索引 0（名称）、7（备注）、8（创建者）**
4. **星系解析**（`TryResolveSystem(string)`）：`EveManager.Instance.GetEveSystem(s)`，
   要求**整字段精确匹配**，不做子串匹配。不做中文反查，理由见 §3.3
5. 解析不出星系的行 → 收集到「无法解析」列表原样回显

### 3.3 为什么不做中文星系名反查

`EveManager.Translations` 是**单向 EN→ZH**（`data/Translation.csv`，8609 行）没有反查表，`NameToSystem` 只有英文键，所以中文客户端显示的星系名会 100% 解析失败。

该论证针对的是帝国区，而本功能只在 nullsec 用：

| 口径 | 数量 |
|---|---|
| nullsec 星系总数（security ≤ 0.0） | 6556 |
| 其中有真·汉字译名的 | **42**（0.64%） |
| 血脉 (Branch) 94 个星系中有汉字译名的 | **0** |

那 42 个绝大多数是 **Pochven 系**（Krirald / Skarkon / Vale / Niarja / Kaunokka / Otanuomi …，原高安低安被吞并所以带真名），其余是 Thera / Zarzakh / Polaris 和几个 NPC null 命名系（Doril / Hemin / Jorund / Utopia / Poitot / Serpentis Prime）。nullsec 主体是 `BKG-Q2` 这类代号，在 CSV 里是恒等映射。

关键在于失败是可见的：解析不出的字段会进「无法解析」列表摆在用户面前（§7），不会静默错到别的星系去。所以反查表只是在把一个可见的非问题变成静默成功，而那个场景不发生。真碰上了再加也是 5 行。

另外 `Translation.csv` 本身有脏行 —— 第 3698 行是 `GME-PQ,ME-PQ`，译名把开头的 G 吃掉了。按纯字符串比对统计会把这类行算成「译名」（最初的 2055 条即因此虚高，按汉字过滤后为 1998 条）。这是不该拿它当解析源的又一个理由。

### 3.4 为什么不能「扫描所有字段取第一个命中的」

原始设计依据是「8437 个星系名与 1174 个星座名零碰撞」（已实测确认交集为 0，星系∩星域、星座∩星域同样为 0）。但该论证**回答了错误的问题**：真正的碰撞源不是星座列，而是**第 0 列（名称）由位标作者自由输入**，且「用目的地名字命名位标」是 EVE 玩家极常见的习惯。

文本来自聊天频道的陌生人 —— 一条名为 `Jita` 的位标会静默把整行劫持到 Jita，用户在结果列表里看到的是个真实存在的星系，只是错的那个，毫无征兆。

因此解析必须**按列号优先**，全字段扫描只作为列数不符时的兜底，且排除自由文本列。

## 4. 算法

### 4.1 总览（一阶段混合代价矩阵）

```
1. 解析 + 去重  → 目标集合 T（N 个星系），起点 S = 当前角色所在星系
2. 单源 BFS × (N+1) → 星门距离矩阵 D[i][j]，同时记录每条最短路径的完整星系序列
3. LY 矩阵 L[i][j] ← GetRangeBetweenSystems（N² 次，很便宜）
4. 混合代价矩阵：
       cost[i][j] = ( emptyRun(i,j) ≥ K  &&  L[i][j] ≤ MaxLY  &&  J < D[i][j] ) ? J : D[i][j]
   其中 emptyRun(i,j) = 门路径 i→j 上最长的「连续非目标星系」段长度
        J = 旗舰跳代价，默认 10，见 §4.3.1
5. 从 S 出发覆盖全部 T 的开放路径 TSP → 最近邻构造 + 2-opt 改进
6. 展开成完整星系序列；cost==1 的相邻目标对 = 旗舰跳
7. 在每次旗舰跳处切开 → 若干条「线」
```

### 4.2 为什么是一阶段而不是两阶段

两阶段（先按纯门距算 TSP，再把长空段换成跳）会被下面这个反例推翻：

> 目标 A、B、C，起点 S。设 `gate(A,B)=30` 且 A、B 相距 5LY（可跳）；`gate(A,C)=12`、`gate(C,B)=12`，C 与 A、B 均相距 8LY（不可跳）。
> 两阶段的第一步比较 `S→A→C→B`（24 跳）与 `S→A→B→C`（30+ 跳），选前者。第二步在 A→C、C→B 上找不到 ≤6LY 端点，一次跳都插不进去，最终代价 **24**。
> 而 `S→A→B→C` 里 A→B 会塌缩成 1 次跳跃，最终代价约 **13**。
>
> **门距最优解的最终代价比次优解差 85%**，且第二步只替换不重排，补不回来。

这不是罕见构造：能跳的点对恰恰是「空间上近、星门上远」的点对，正是纯门距 TSP 会主动避开的那类边。实测跳跃图 6LY 内有 166618 条无向边、平均度 78.6，此类点对海量存在。

一阶段混合矩阵让目标函数从头到尾只有一个，代码反而更短（少一个扫描阶段）。

### 4.3 跳跃触发规则

**`emptyRun(i,j) ≥ K 且 LY(i,j) ≤ MaxLY`**，K 默认 **2**，界面上可调。

`emptyRun(i,j)` = i 到 j 的星门最短路径上，**不属于目标集合 T** 的星系连续出现的最大长度（不含 i、j 本身）。

**K 取 2 而非 3**：血脉 (Branch) 区总共只有 94 个星系，42 个目标占 45%。星门图平均度 2.64（13776 条有向边 / 8437 节点），路径是细长链，凑不出 3 个连续空系。按 K=3，在用户唯一验证过的数据上**一次旗舰跳都插不进去，永远只输出 1 条线**，决策「分线」和整个线的 UI 概念全是死代码。

**已知权衡**：K=2 是最宽松取值 → 可跳边最多 → 切出的线最碎。K 是界面滑块，重算即时反馈线数。

### 4.3.1 旗舰跳代价 J

**K 决定哪些点对有资格跳，J 决定跳到底划不划算。两者正交，都需要。**

跳的代价若写死为 1 会连跳。血脉区的实例 `KJ-QWL →跳→ I-7RIS →跳→ 5-P1Y2`：

| FROM | TO | 星门 | LY | emptyRun | 判定 |
|---|---|---:|---:|---:|---|
| KJ-QWL | I-7RIS | 10 | 5.47 | 7 | 可跳 |
| I-7RIS | 5-P1Y2 | 12 | 4.10 | 7 | 可跳 |
| KJ-QWL | 5-P1Y2 | **2** | 2.13 | 1 | 只能走门 |

代价=1 时优化器算的是 `1+1=2` 对 `2+1=3`，于是选了连跳 —— **完全正确地执行了错误的规则**。现实里没人会为省 2 跳星门去点两个 cyno 烧疲劳。更要命的是连跳产出的是「一条线一个点」，与用户最初那句「每条线路里的点最大化」正好相反。

K 治不了它 —— 该点对的 emptyRun 是 7，K 要调到 8 才挡得住，而 K=8 时全局只剩 4 对可跳，等于关掉功能。

实测标定（血脉区 42 目标 / 1722 有序点对）：K=2 下 112 对有资格跳，它们的星门绕路距离 min 3 / 中位 9 / max 17。

| J | 仍值得跳的对数 |
|---:|---:|
| 1（初版） | 112 —— 全跳，连跳 |
| 8 | 66 |
| **10（默认）** | **36** |
| 12 | 8 |
| 20 | 0（等于关闭） |

可用区间 8~12。注意这些数字是血脉区这一组数据标出来的，换星域要重新看。J 是界面滑块（1~25），标签写成「星门绕路 > J 跳才跳」，比抽象的「代价」直观。

**歧义消解**：因为跳跃判定是**按目标点对**（i,j）做的，而非在展开后的序列上扫描，所以原设计的三处歧义自动消失：
- 跳跃端点永远是两个目标点，不会切在无意义的空系上
- 门路径穿过第三个目标点 → 该目标会打断 run，`emptyRun` 自然变小，这是正确行为（顺路能收的点不该跳过）
- 子段歧义不存在 —— `emptyRun` 取最长连续段，是确定值

### 4.4 距离矩阵：不复用 `Navigation.Navigate`

**必须自写单源 BFS**，理由有三，均已核实：

1. **返回值三态混淆** —— [`Navigate`](../EVEData/Navigation.cs) 在 `CurrentNode == End` 时提前 `break`（:339）。当 `From == To` 时起点从未被赋予父节点，`End.NearestToStart` 为 null（:540），`Route` 保持为空，函数返回的是**空 List 而非 null**。「不可达」和「父链超 2000 的 rootError」同样返回空 List。三种情况挤在同一个返回值上，`sysList.Count - 1` 全都等于 **-1**。负权进入最近邻构造会让算法优先选自环；进入 2-opt 会让改善量恒为正而无限翻转。
2. **21 倍冗余** —— `Navigate` 是单源单汇且提前终止，无法复用一次搜索的全部距离。逐对调用 N=42 就是 903 次 Dijkstra，而单源 BFS 只需 43 次即可填满矩阵。N=200 时是 20301 次。
3. **虫洞星系触发全图抽干** —— 全服有 **3005 个 J 空间星系**，与已知空间零星门连接。位标里出现虫洞系并不罕见。只要有一个，所有涉及它的点对都会把整个 5432 节点的已知空间连通分量抽干（`OpenList` 空才退出，永远碰不到提前终止）。

**自写 BFS 的额外收益**：可以在 BFS 内部**硬排除高安**（见 §4.5），并且同一次搜索就能顺便记下路径用于 `emptyRun` 计算。

矩阵约定：`D[i][i] = 0`；不可达记 `int.MaxValue`（在混合矩阵里视为不可跳且不可达，该点进入「不可达」列表）。

### 4.5 安全等级过滤

用户明确「不会去高安，我们只会在 nullsec 做这个事」。

现有 `Navigation.Navigate` 的默认 `RoutingMode.Shortest` 对所有星系一律返回代价 1，会毫不犹豫穿高安；`PreferLow` 也只是 1000 的软惩罚，路不通时照穿。

**自写 BFS 中硬排除 `TrueSec > 0.45` 的星系**（与 `CreateStaticNavigationCache` 建跳跃邻接时的排除阈值一致，该处同时排除了 Pochven 和 Zarzakh）。

### 4.6 不使用 `NavigateCapitals`

第 4 步只需要判断两点直线距离，用 `EveManager.GetRangeBetweenSystems(a, b)` 即可，N² 次，成本可忽略。

绝对**不要**在循环里调 `NavigateCapitals`：它每次调用都对全部 8437 个节点做完整重置、没有提前终止、主循环里 `OpenList.Min()` / `.First()` / `.Remove()` / `.Contains()` 全是 `List<MapNode>` 上的 O(n) 扫描。跳跃图平均度 206，单次调用约 10⁸~10⁹ 次比较。

同理不要在 O(N²) 循环里调 `GetSystemsWithinXLYFrom` —— 每次调用是 8437 次 `DecimalEx.Sqrt`（软件实现的十进制开方）。

### 4.7 TSP 求解

- **构造**：最近邻，从 S 出发
- **改进**：2-opt（开放路径版本，起点固定，终点自由）+ Or-opt（可选）
- **候选评分**：**必须重新测量整条路线**，不能用常见的 O(1) 两条边界边增量。那个增量式只对对称矩阵成立，而本矩阵不对称 —— `emptyRun(i,j)` 读的是以 i 为根的 BFS 树、`emptyRun(j,i)` 读的是以 j 为根的树，当一对点之间存在多条等长最短路时，两个方向对「这段是否可跳」会给出不同答案。翻转一段会把段内每条边都反向，增量式完全不看这些边，因而会接受让总代价变差的交换。重新测量是 O(N)/候选，这个规模下可忽略
- **规模**：N=42 时矩阵 43×43，2-opt 单趟 O(N²) 次候选 × O(N) 评分，毫秒级。N=200 仍然轻松。
- **收敛**：迭代直到一趟无改进，或达到迭代上限（防病态输入死循环）

**必须在后台线程跑**（`Task.Run`），完成后 `Dispatcher` 回 UI。现有代码没有后台寻路的先例可抄 —— `CapitalRoute.Recalculate()` 是在按钮 `Click` 里同步调的（`MainWindow.xaml.cs` 多处），照抄会冻结整个 App。

### 4.8 孤点过滤

某个位标在 **N 跳星门内**（**不含旗舰跳** —— 「但它在跳跃射程内」正是要排除的情形）没有任何其它位标，就放弃它。为它跑一趟是独立行程，让路由为它把整条线掰弯不值得。

- **起点也算「伴」**：一个就在你驻地隔壁的孤零零位标不是绕路
- **单趟扫描就够**：互相靠近的一对会互相保住，而一个点只有在完全没有「未被丢弃的伴」时才会被丢弃，所以不需要迭代到不动点
- **位标多的星系豁免**：位标数 ≥ M 的星系永不当孤点丢弃（M 默认 3，滑块 2~10）。几个目标挤在一处本身就是跑这一趟的理由，不是这条过滤要抓的孤零零离群点。实现上守 `M > 0` —— 直觉写法 `count >= 0` 会保护所有星系、把过滤器悄悄关掉
- **绝不静默**：被丢的点进面板的「孤点（已放弃）」框，状态栏也计数
- 复选框控制开关 + 半径滑块（1~15，默认 5）。关闭时向求解器传 `isolationJumps = 0`

**实测标定**（血脉区 42 目标，每个点「最近的另一个位标」有多少跳星门）：

```
 1 跳 : 35 个  ###################################
 2 跳 :  6 个  ######
 8 跳 :  1 个  #   ← KMC-WI
```

断崖极其明显 —— 41 个点最远 2 跳内就有伴，KMC-WI 要 8 跳。N 取 2~7 之间任何值结果都一样，只丢 KMC-WI，所以默认值不敏感。

K=2 / J=4 时会出现一条横跨半张图的 `JRZ-B9 → KMC-WI` 旗舰跳。查下来 KMC-WI 有 8 个可跳邻居，J=4 时**代价全都是 4，完全平局**，选中 JRZ-B9 纯属任意平局决胜。真正的问题不是怎么接它，而是该不该去。

**仍存在的模型缺口**：扁平代价 J 把「这一跳有多长」的信息扔了 —— 3.94 LY 和 5.68 LY 的跳在优化器眼里一个价，非孤点场景下仍会出现看起来任意的选择。修法是让跳的代价带一个 LY 尾数做平局决胜（把代价整体放大 100 倍，低位放 `LY×10`）。**尚未实施。**

### 4.9 废弃率

两个口径都报，头条数字用位标口径：

```
系统口径 = (解析星系数 − 计划访问星系数) / 解析星系数
位标口径 = (解析位标数 − 计划访问位标数) / 解析位标数     ← 面板头条
```

一个星系装 1~4 个位标（实测：25 个装 1 个、10 个装 2 个、5 个装 3 个、2 个装 4 个），所以丢一个星系并不等于丢固定比例的活。**丢掉一个 4 位标星系，系统口径报 1/42 = 2%，位标口径报 4/68 = 5.9% —— 差三倍。** 只报系统口径会在"被丢的恰好是位标密集的星系"时系统性少报。

**计划访问数从最终路线反推**（把每条线的 `Targets` 加起来），而不是把 `孤点数 + 不可达数` 加起来。故意绕这一圈：万一哪天有目标既没进孤点表也没进不可达表就消失了，废弃率会把它报出来而不是掩盖掉 —— 等于给自己留了个审计。

**落在起点上的位标算「已计划」**，不算废弃 —— 求解器会把它从目标集合里去掉（你已经站在那儿了），但你确实到过。

## 5. 数据模型

新面板**维护自己独立的路线数据**，不复用 `LocalCharacter.Waypoints` / `ActiveRoute`。

**理由**：每个 `LocalCharacter` 只有一份 `Waypoints` 和一份 `ActiveRoute`，地图叠加层画的也是这一份（`RegionControl.xaml.cs` 直接遍历 `ActiveCharacter.ActiveRoute`）。若复用：

- 应用某条线会清掉用户在 Route 面板里已有的航点，且用户无从得知是哪个面板干的
- `Location` 的 setter 在每次位置变化时置 `routeNeedsUpdate`，后台线程随即按**纯星门最短路**重算整条 `ActiveRoute`，把精心切好的「线」重新展开
- 后台还会 `Waypoints.RemoveAt(0)` 移除已到达的航点
- 任一 `Use*Routing` 开关被碰会同时置 `esiRouteNeedsUpdate`，静默重推 ESI，覆盖已应用的线

建议类型（放 `EVEData/`）：

```csharp
public class BookmarkRoute          // 一次规划的完整结果
{
    public List<RouteLine> Lines            { get; }   // 按旗舰跳切出的段
    public List<string>    UnreachableSystems { get; } // 门不可达且 >MaxLY
    public List<string>    UnparsedLines   { get; }    // 解析失败的原始行
    public Dictionary<string,int> BookmarkCounts { get; } // 星系 → 位标条数
}

public class RouteLine
{
    public List<Navigation.RoutePoint> Points { get; }  // 含中途非目标星系
    public List<string> Targets { get; }  // 本线要访问的位标星系，按顺序；ESI 推送和列表都用它
    public decimal EntryJumpLY { get; }   // 跳进这条线的距离；无跳跃进入时为 0
    public int  TargetCount   { get; }
    public int  GateJumps     { get; }
}
```

`RoutePoint` 复用现有类型（`SystemName` / `GateToTake` / `LY`），`GateToTake` 用 `GateType.StarGate` 和 `GateType.JumpTo` 区分门段与跳段。

**角色切换**：清空面板结果，要求重新计算（起点变了，结果失效）。
**飞行途中位置变化**：**冻结**已算好的路线，只高亮当前进度，不重算。

### 6.2 地图绘制

在 `RegionControl` / `UniverseControl` 上画出路线，**门段与跳段用不同样式**（跳段建议虚线 + 标注 LY）。

### 6.3 ESI 航点推送 —— 每次只推一条线

用户最初选「一次推全部」，被以下事实说服改为逐线：

> 游戏内航点**只认星门**。路线在旗舰跳处是断开的（比如线 1 结束在 `T-Q2DD`、线 2 从 `9F-7PZ` 开始，直线 5.2 LY）。全部推进去，游戏会用星门把两段连起来，可能是 20 跳绕路，画出来的航线跟计划完全不符。

**必须先清空**：现有推送代码调的是

```csharp
SetAutopilotWaypointAsync(auth, firstRoute, false, SysID)   // LocalCharacter.cs:933
```

ESI 签名是 `Waypoint(destination_id, add_to_beginning, clear_other_waypoints)`（见 `External/ESI.NET/ESI.NET/Logic/UserInterfaceLogic.cs:67`）。所以 `firstRoute` 传给的是 **`addToBeginning`**，而 **`clearOtherWaypoints` 恒为 false**。对照 `LocalCharacter.cs:807` 的清路径分支传的是 `(auth, true, true, s.ID)` —— 两处写法不同证明这是有意区分的。

结果：**逐线推送根本不隔离**。推第二条线时不会清掉第一条的残留，游戏内变成拼接，自动驾驶照样跨着跳跃缺口走门 —— 正是用户要避免的。

**实现**：应用一条线时，第一个航点用 `clearOtherWaypoints = true`，后续用 `false`。

### 6.4 推送不复用 `LocalCharacter.AddDestination`

新功能**自己封一层 ESI 推送**，理由：

1. `AddDestination`（`LocalCharacter.cs:502-518`）只把 `Waypoints.Clear()` 放在 `lock (ActiveRouteLock)` 里，紧接着的 `Waypoints.Add(...)` **在锁外**。后台线程在 `UpdateActiveRoute` 里读 `Waypoints.Count` 和 `Waypoints[0]`。跨线程无同步读写 `List<T>` 会让 Count 与实际长度短暂不一致 → `ArgumentOutOfRangeException`
2. `UpdateActiveRoute` 声明为 `private async void`，被无 `await` 调用。`async void` 里的异常在无 `SynchronizationContext` 的后台线程上会**直接终止进程**
3. 连续应用一条线意味着短时间内几十次 `AddDestination`，把该竞态放大到必现级别
4. 现有推送 `catch { }` 吞掉一切（403 缺 `esi-ui.write_waypoint.v1` scope、420 限流、网络超时），失败时界面毫无提示；还绕开了 `ESIHelper.TryUpdateEsiRateLimitFromResponse` 的限流统计；用的是 `Thread.Sleep(200)` 而非 `await Task.Delay(200)`，42 个航点 = 8.4 秒阻塞后台更新线程，期间该角色位置/在线状态/舰队信息全部停更

新封装要求：走 `ESIHelper` 统计限流 · `await Task.Delay` 不阻塞 · 失败在面板上明确报错。

## 7. 边界情况

| 情况 | 处理 |
|---|---|
| 解析不出星系的行 | 收集原始行，面板上「无法解析: N 行」可展开查看 |
| 同一星系多个位标 | 合并为一个目标点，列表显示「BKG-Q2 (3 个位标)」，悬停显示三个原始名称 |
| 星门不可达且 > 射程 的点 | 单独归入「本次不可达」组，不拖垮整个规划 |
| 虫洞 (J 空间) 星系 | 归入不可达组（与已知空间零星门连接） |
| 高安星系出现在位标里 | 归入不可达组（BFS 已硬排除高安）并注明原因 |
| 目标数 0 | 提示「没有解析到任何星系」，不进入求解 |
| 目标数 1 | 直接输出单点路线 |
| 起点本身就在目标集合里 | 视为已访问，从待访问集合移除 |
| 避开星系列表 | BFS 中排除，与高安过滤同一机制 |
| 孤点（N 跳星门内无其它位标） | 归入「孤点（已放弃）」组，计入废弃率。见 §4.8 |
| 计算耗时过长 | 后台线程 + 进度提示 + 可取消 |
